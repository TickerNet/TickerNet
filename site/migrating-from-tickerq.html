Migrating from TickerQ

TickerNet is TickerQ's code as of commit 3acd0f31 with every TickerQ name changed to TickerNet. Your data carries over: table, collection and key names are the same. Your code needs new package references and namespaces, and a few names your monitoring or proxy may depend on have changed.

Before you start

  • Which TickerQ. This guide is for TickerQ 10.4.x and earlier open-source releases. It was checked against the TickerQ code at the fork point, commit 3acd0f31, which is four commits after the 10.4.0 package.
  • .NET 10 or later first. TickerNet targets .NET 10 and .NET 11 (ADR 0012). If you are on a TickerQ 8.x or 9.x release for .NET 8 or 9, move your app to .NET 10 or 11 first (ADR 0006).
  • Packages. TickerNet's packages are on nuget.org. Getting started shows how to add them.
  • One behaviour change: jobs started at once outlive the call that added them. When a job is dispatched straight away, for example a time job added with AddAsync or AddBatchAsync for now or the next second, or a cron run started from the dashboard, it no longer runs with the CancellationToken you passed to that call. It runs with the host's stopping token. In TickerQ, cancelling that token, for example by the end of the HTTP request that added the job, could cancel the job or leave it InProgress. To cancel one job, use TickerCancellationTokenManager.RequestTickerCancellationById.
  • TickerQ Hub. TickerQ Hub, a hosted service with its own terms, isn't supported (ADR 0005). If you ran jobs on remote workers with TickerQ.RemoteExecutor and TickerQ.SDK, TickerNet does it without a hosted service: TickerNet.Hub in the scheduler and TickerNet.Worker in the workers. Jobs stored as function@node keep working. See section 06 and Remote workers.
TickerQ 10.5.0 and later are a different product. They are released under a commercial license, as are the matching 8.5.0, 9.5.0 and 11.5.0 builds. Nothing from those versions is in TickerNet, and features added there do not exist here. This guide does not cover them.

If you are on 10.4.0, you also pick up the four TickerQ commits that came after it and before the fork: ActivitySource tracing built into the core packages (EnableActivitySource()), OpenTelemetry packages at 1.15.3 or later, a change to how the dashboard sends cron runs over SignalR, and the new MongoDB store.

02

Namespaces and API

The rename replaced TickerQ with TickerNet everywhere, in any letter case, and changed nothing else.

Every namespace moved: TickerQ.DependencyInjection is now TickerNet.DependencyInjection, TickerQ.Utilities.Base is now TickerNet.Utilities.Base, and so on. TickerQ.TickerQThreadPool is now TickerNet.TickerNetThreadPool. Public types and members with TickerQ in their name changed the same way:

Names that did not change. Anything without TickerQ in its name kept it: AddOperationalStore, AddStackExchangeRedis, AddDashboard, AddOpenTelemetryInstrumentation, EnableActivitySource, MapTicker, [TickerFunction], TickerFunctionContext, the managers, the entities and TickerHelper. Names that start with TickerQuery or contain TickerQueryable, such as ITickerQueryable, TimeTickerQueryFilter and CronTickerQueryFilter, mean "ticker query" and were left alone.

Doing it in one pass. Commit your work first, then run this from your repository root. It renames TickerQ in C#, project and JSON files and .editorconfig, leaves TickerQuery… names and EF Core migration IDs alone, and changes TQ0nn diagnostic IDs to TN0nn. Review the diff before you commit it.

shellone-pass rename, needs git and perl
git grep -lz -e TickerQ -e 'TQ0[0-9][0-9]' -- '*.cs' '*.csproj' '*.props' '*.json' '.editorconfig' \
  | xargs -0 perl -pi -e 'next if /\[Migration\(/; s/TickerQ(?!uer)/TickerNet/g; s/\bTQ0(\d\d)\b/TN0$1/g'

It does not touch lower-case strings such as "tickerq" or "/tickerq/dashboard"; section 04 lists those. It also leaves TickerQ's version numbers on package references, so swap those for TickerNet project references.

05

EF Core migrations

The database needs no change. Your migration files do.

Migrations you generated with TickerQ refer to TickerQ.EntityFrameworkCore.DbContextFactory, typeof(TickerQDbContext) and, in the model snapshot, entity names such as "TickerQ.Utilities.Entities.TimeTickerEntity". Rename those to TickerNet so the files compile and the snapshot matches the new model. The one-pass command in section 02 does this.

Leave every migration ID in [Migration("…")] as it is, even if it says TickerQ. EF Core records applied migrations by ID in __EFMigrationsHistory. A changed ID looks like a new migration, and applying it would try to create tables that already exist.

To check, add a throwaway migration. If its Up() and Down() are empty, the model matches the database and you can remove it. If not, read it before you apply anything.

shellcheck that nothing changed
dotnet ef migrations add CheckTickerNetRename
# Inspect the new file: Up() and Down() should have no operations.
dotnet ef migrations remove
06

Coming from TickerQ Hub

Only if you ran jobs on remote workers with TickerQ.RemoteExecutor and TickerQ.SDK.

TickerNet has no hosted hub: the scheduler is the hub. Remote workers covers set-up and behaviour in full, and ADR 0009 records the design.

  • Scheduler. Replace TickerQ.RemoteExecutor with TickerNet.Hub: call AddTickerNetHub with a shared secret inside AddTickerNet, and app.MapTickerNetHub(). The scheduler must accept HTTP/2.
  • Workers. Replace TickerQ.SDK with TickerNet.Worker: call AddTickerNetWorker with the scheduler's address, the same shared secret and a node name. Workers connect to the scheduler, not to TickerQ Hub, and need no hub API key. TickerQ.SDK can't connect to a TickerNet scheduler.
  • Use the same node names. Stored jobs named function@node run on the TickerNet worker whose node name matches, with the same spelling.
  • Data. No change: the function@node naming rule and the IsSystemPaused cron column work as before.
  • Code. SdkOfflineSkipException still works but is obsolete; use WorkerOfflineException. The TickerFunctionProvider hooks are kept.
  • Behaviour. The scheduler, not the worker, now runs retries and records every status. Logs from a function stay in the worker's own logging; they aren't forwarded to the dashboard.

Checklist

  • Your app runs on .NET 10 or .NET 11.
  • TickerQ package references are replaced with the matching TickerNet packages.
  • Namespaces, types and members are renamed, with TickerQuery… names and migration IDs left alone.
  • TQ0nn suppressions and severities now say TN0nn.
  • EF Core migration files compile, and a check migration comes out empty.
  • Redis: you chose to keep or change the InstanceName prefix, and changed any "tickerq" keyed-service lookups.
  • Dashboard: proxy and access rules use the new path, or you set the old one. Old links redirect on their own.
  • Tracing listens to TickerNet with AddTickerNetSource(). Trace queries and alerts use the new names, or you turned on useTickerQNames: true. Log searches and log levels use the new names.
  • If you used TickerQ Hub: the scheduler uses TickerNet.Hub, workers use TickerNet.Worker with the same node names and the shared secret, and SdkOfflineSkipException is replaced with WorkerOfflineException.
  • Code that cancelled a just-added job through the token passed to AddAsync now uses TickerCancellationTokenManager.RequestTickerCancellationById.
  • All nodes are upgraded in the same deployment.
